# PipeView optional XML authoring

The optional `sdk/pipeview/markup` frontend maps the current declarative view
profile to the same typed checker, document and state/action definition as
PipeLang views. It introduces no rendering or state runtime. PipeLang remains
the primary authoring syntax. This is PipeView XML, with explicit rules below.
Qt `.ui`, QML, HTML, styles and general XML templating are separate work.

For the settings screen, the XML starts like this:

```xml
<View name="SettingsView" profile="pipelang.pipeview.source.v2">
  <State name="playerName" type="string" value="Rider"/>
  <State name="vsync" type="bool" value="true"/>
  <Action name="nameEdited" payload="string" operation="set" target="playerName"/>
  <Action name="vsyncEdited" payload="bool" operation="set" target="vsync"/>
  <Action name="save" operation="save"/>
  <Action name="revert" operation="revert"/>
  <Column id="root">
    <TextField id="name-field" value="{bind playerName}" changed="{nameEdited}"/>
    <Toggle id="vsync-toggle" label="VSync" value="{bind vsync}" changed="{vsyncEdited}"/>
    <Label id="save-status" value="{bind save.status}"/>
    <Row id="actions">
      <Button id="save-button" label="Save" clicked="{save}"/>
      <Button id="revert-button" label="Revert" clicked="{revert}"/>
    </Row>
  </Column>
</View>
```

The complete equivalent to the primary settings view lives in
`examples/settings/SettingsView.xml`. Build that application with
`-DPIPEVIEW_VIEW_SYNTAX=xml`; the default remains `pipelang`. The selector chooses
one complete source file. It does not merge them or watch for changes.

Use the optional `pipelang-viewc` tool with absolute paths:

```sh
pipelang-viewc --source /project/SettingsView.pipe --emit xml --output /tmp/SettingsView.xml
pipelang-viewc --syntax xml --source /tmp/SettingsView.xml --emit pipelang --output /tmp/SettingsView.pipe
pipelang-viewc --syntax xml --source /tmp/SettingsView.xml --output /tmp/PipeViewDocument.hpp
```

The input syntax is explicit: `--syntax pipelang|xml`. The output choice is
`--emit header|pipelang|xml`. Defaults preserve the existing PipeLang-to-header
behavior. Source conversion validates the shared component profile before
publishing. A source conversion receipt uses `pipelang.pipeview.convert.v1`;
header generation retains `pipelang.pipeview.export.v1`. Both record input and
output hashes and selected tool/component identity. Receipts are completion
markers; consumers must compare the generated bytes with their digest.

The optional native lexer processes generated canonical PipeLang when input is
XML. Go remains the reference parser/checker. Typed semantic errors map back to
an authored XML element's opening tag, preserving the diagnostic code and message.
Their structured diagnostics retain the generated PipeLang span as related
context. Original UTF-8 byte spans resolve through the original source file into
line, column and editor UTF-16 positions, including multiline opening tags.
This is element precision; individual attribute positions remain future work.
XML admission failures are structured source diagnostics with code `PV1001`,
resolved authored positions and bounded UTF-8 spans. Invalid UTF-8 retains the
compiler's `PL0001` admission diagnostic. Native lexer, lexical and unmapped
failures keep their generated-source identity rather than being reported as
XML type errors.

## Mapping and bounds

`View` requires a name and an explicit source profile. Version 1 uses `Event`
declarations; version 2 uses typed `Action` declarations. `State`, `Event` and
`Action` precede exactly one component tree. State `type`/`value`, event payloads
and action operations have the same meaning and restrictions as the primary
source profile. No expression evaluation occurs in XML.

Component `id`, `text` and `label` attributes contain literal text, including
literal braces. `value` uses `{bind identity}`. `changed` and `clicked` use
`{actionOrEvent}`. XML escapes protect characters such as `&` and `<`; they do
not add a second binding syntax. Unknown attributes and unsupported properties
fail explicitly.

Inputs and converted outputs are bounded to 64 KiB of valid UTF-8. The existing
128-element, eight-level tree and independent 128-state/event/action limits
apply. XML declarations, processing instructions, directives/DTD, namespaces,
custom entities, non-whitespace mixed content and multiple roots are refused.
The frontend reads no external resources. Unsupported XML 1.0 characters fail
conversion rather than being replaced.

Round trips preserve declaration meaning, stable IDs, literal values, typed
bindings, action wiring and component order. Formatting and comments are not
preserved. Canonical PipeLang formatting belongs to the compiler; XML conversion
belongs to the optional frontend. Neither introduces an engine dependency into
the compiler, core UI model, inspection or test harness.


The [verification record](../research/pipeview-markup.md) describes the installed
SDK, native Save/reopen and Go reference checks for this bounded slice.


## Machine-readable failures

`pipelang-viewc --diagnostics json` writes one JSON object to stderr on failure:

```sh
pipelang-viewc --diagnostics json --syntax xml \
  --source /project/SettingsView.xml --output /tmp/PipeViewDocument.hpp
```

The object has contract `pipelang.pipeview.diagnostics.v1`, `failure_kind` and
`diagnostics`. Structured compiler/frontend errors use `failure_kind: "source"`
and the existing resolved diagnostic fields: code, category, severity, message,
primary file/range and related locations. Authored XML type errors keep their
generated-source location as related context. XML admission uses `PV1001`; its
category is `source`, covering the bounded XML profile as well as XML syntax.

Other failures use `failure_kind: "tool"`, an empty diagnostic array and a
`message`; no source range or language code is invented. These include ordinary
I/O errors, flag errors, process failures and tool-side capacity/conversion
refusals that do not carry a structured compiler diagnostic. A typed lexer
diagnostic retains its actual generated-source identity.

Failure exits with status 2. Success stays silent and exits 0; generated headers,
converted sources and completion receipts keep their existing contracts. The
default `--diagnostics text` retains readable error output. Put format selection
before an invalid flag: only flags reached by the normal parser are selected.
An invalid diagnostics mode produces a text error. Normal help remains readable
in text mode. This is a command-line interface, with no runtime endpoint.

For an oversized XML library input, its size error resolves at offset zero using
a bounded prefix of the actual input. Admitted-size inputs retain their full
original bytes for diagnostic resolution. Element-level typed mapping and
attribute-level precision limits above remain unchanged.
